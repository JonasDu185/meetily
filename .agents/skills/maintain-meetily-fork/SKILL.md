# 维护 Meetily Community Fork

## 开始前

1. 读取仓库根目录 `AGENTS.md`。
2. 读取 `docs/UPSTREAM.md`、`docs/LEGAL.md`、`docs/ACCEPTANCE.md` 和 `docs/BUILD_BASELINE.md`。
3. 检查当前分支、工作区状态、远程仓库和 `HEAD`。
4. 保留用户已有改动；发现重叠修改时先停止并说明。

## 硬性边界

- 仅使用 Meetily Community 的 MIT 源码和许可证允许使用的依赖。
- 不复制、反编译、逆向或借用 Meetily Pro 的闭源代码、图标、截图和商业资产。
- 可以根据公开产品行为独立实现同类功能，但实现和测试必须来自本仓库及公开 API。
- 不未经确认安装依赖、初始化子模块、下载模型、修改全局环境、删除文件、提交、推送或创建远程仓库。
- 不在 `main` 上直接开发；使用 `feature/*`、`fix/*`、`chore/*` 或 `sync/*` 分支。
- 保留 `LICENSE.md` 和原版权声明；新增第三方组件时记录许可证和来源。
- 个人版默认关闭遥测和官方自动更新；不得未经用户确认自动录音。
- 代码注释和 commit message 使用中文。

## 变更流程

1. 固定范围：写清本轮目标、不做事项、验收标准和回滚方式。
2. 建立分支：从已确认的稳定基线创建单一目的分支。
3. 先读后改：定位当前实现、调用链、测试和上游相关 Issue。
4. 小步实现：优先修改 Community 主应用 `frontend/`；`backend/` 仅作历史参考。
5. 分层验证：先做针对性测试，再做受影响模块测试，最后做本机流程验收。
6. 检查差异：确认没有意外品牌资产、遥测、官方更新地址、付费 API 或秘密信息。
7. 汇报结果：说明改动、验证、剩余风险和回滚方法；不把“未测试”写成“已完成”。
8. 完成一个功能或连续修改几轮后，提醒用户运行 `/simplify`。

## 同步上游

1. 确认工作区干净或已有改动已妥善保存。
2. 只从 `upstream` 获取官方更新。
3. 创建 `sync/upstream-日期或版本` 分支，不直接改 `main`。
4. 比较许可证、构建系统、数据库迁移、音频管线、模型目录和 Tauri 配置。
5. 合并上游后逐项解决冲突，禁止用整文件覆盖跳过判断。
6. 执行 `docs/ACCEPTANCE.md` 中受影响项目的验证。
7. 记录新上游提交号、冲突决策和仍需人工验证的内容。
8. 经用户确认后再提交、合并或推送。

## 当前优先级

- 麦克风与系统声音稳定录制、内部来源分轨和混合录音。
- 录音导出、Markdown/PDF 转写导出。
- 本地 Whisper 模型管理和中文转写。
- 中文搜索稳定性。
- 会议检测提醒，必须点击确认后开始录音。
- 长会议、恢复、设备切换和蓝牙兼容性。

会议摘要、大模型接入、具体姓名声纹识别和大规模界面重做不属于当前 MVP。

## 验证最低要求

- Rust：格式检查、相关单元测试和编译检查。
- TypeScript：相关测试、类型检查或构建检查。
- 音频：真实设备录制，检查时长、采样率、缺帧、同步和恢复。
- 导出：重新打开文件，检查中文、分页和可复制文本。
- 搜索：覆盖纯中文、中英混合、表情符号和长文本。
- 会议检测：验证不自动录音、不重复提醒、录音中不二次启动。
